## 2. 技术设计

- 官方 `pytorch/pytorch:2.7.1-cuda12.6-cudnn9-runtime` 作为唯一训练基础镜像；兼容性最终由容器 CUDA 实测确定。
- 固定 Transformers 4.53.3、PEFT 0.16.0、Accelerate 1.9.0 等直接依赖；不额外安装替代 PyTorch。
- LoRA + BF16 + SDPA + gradient checkpointing；不要求安装 FlashAttention CUDA 扩展。
- 模型编码遵循 Qwen 官方最后 token 池化、L2 normalization、query 指令和 document 无指令约定。
- 使用显式负样本 InfoNCE，每个 query 独立候选集合，防止不加区分地引入 in-batch 假负例。
- 数据治理与模型训练分离，为 ReRank/LLM 复用下载、文档处理、数据版本和分组能力。

### 4.2 建立 SSH 反向转发

工作机单独一个 PowerShell 窗口，保持运行：

```powershell
ssh -N -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -R 127.0.0.1:17897:127.0.0.1:7897 cdky@192.168.88.91
```

连接方向：`91 服务器 127.0.0.1:17897 → SSH 加密通道 → 工作机 127.0.0.1:7897 → 官方 Hugging Face/Docker Hub`。`-R` 左边地址在服务器，右边地址由工作机 SSH 客户端连接；`-N` 不启动远端 shell。代理只绑定服务器回环地址，没有对局域网开放代理端口，也无需修改 sshd 配置。

91 服务器第二个会话验证：

```bash
ss -ltn '( sport = :17897 )'
curl -x http://127.0.0.1:17897 -I --max-time 15 https://huggingface.co
```

实际返回 HTTP 200。普通 Docker bridge 容器里的 `127.0.0.1` 指向容器自身，不能直接使用这个服务器回环端口。因此只有临时下载容器使用 `--network host`，再给该进程传入 `HTTPS_PROXY=http://127.0.0.1:17897`。训练容器保持默认独立网络。

若 SSH 显示 remote port forwarding failed，先通过 `ss` 核查端口占用，选择另一个空闲端口并同步修改所有代理 URL；不要停止不属于本工程的进程。若端口存在但 curl 失败，依次检查工作机代理、SSH 窗口是否仍连接、服务器显式代理 curl；不要直接改 Docker daemon。`HTTPS_PROXY` 的值使用 `http://` 是因为此处为支持 CONNECT 的 HTTP 代理。

### 4.3 官方 PyTorch 基础镜像下载

先尝试的常规方式（91 服务器）：

```bash
docker pull pytorch/pytorch:2.7.1-cuda12.6-cudnn9-runtime > logs/base-pull.log 2>&1
```

实际主层约 3.32 GB，直拉较慢，因此终止本次拉取命令，转为下述已实现的备用流程。不要执行全局 kill、prune 或修改 daemon 代理。已有 Python 镜像无需安装依赖，标准库下载器通过官方 registry 获取并校验所有层：

```bash
docker run -d --name aml-image-fetch --network host \
  --user "$(id -u):$(id -g)" \
  -e HTTPS_PROXY=http://127.0.0.1:17897 \
  -v "$PWD:/workspace" -w /workspace \
  python:3.11-slim python -u scripts/pull_official_image.py
docker logs -f aml-image-fetch
docker wait aml-image-fetch
# 上一步输出必须是 0；非零时先查日志，不继续 load。
docker logs aml-image-fetch > logs/image-download.log 2>&1
docker load -i .cache/official-image/pytorch.tar
docker image inspect pytorch/pytorch:2.7.1-cuda12.6-cudnn9-runtime --format '{{.Id}}'
cat .cache/official-image/provenance.json
```

脚本按 linux/amd64 选择 manifest，校验 config/layers 的 SHA256，再生成 Docker save tar；记录 registry digest。镜像仍来自官方 `pytorch/pytorch`，不是代理站重打包镜像。此路径会同时保留压缩层、解压层和 tar，须预留磁盘。Docker 加载镜像会使用原有 Docker 存储，这是工程容器操作，不涉及主机系统包、配置或驱动变更。

### 7.2 当前运行模型与风险边界

Compose 启用 `pid: host`、`ipc: host`、`network_mode: host` 和 `privileged: true`，挂载整个 `/dev`、`/media`、X11 socket、只读 `/etc/localtime` 及读写工程目录。容器共享宿主机端口、进程和 IPC 视图，容器 root/免密 sudo 具有很高的主机影响能力。这套配置用于受信任的内部开发服务器，不能当作不可信代码的隔离沙箱。

`env.sh` 在 `/proc/sys/kernel/core_pattern` 可写时设置 `/workspace/data/core/core_%e.%p`。91 服务器实测宿主机与容器读取值相同，说明这是宿主机级内核设置；停止容器不会自动恢复。`ipc: host` 下实际使用宿主机 `/dev/shm`，因此 `DOCKER_SHM_SIZE=16gb` 不代表独立的 16GB shm，只保留为风格一致和未来切回私有 IPC 的参数。`GPU_ID` 仍提交 NVIDIA device reservation，但 privileged 加整个 `/dev` 挂载时不构成严格的 GPU/设备安全边界。

容器主进程和训练命令仍以映射用户 `1000:1000` 运行。实测普通进程 `CapPrm=0`、`CapEff=0`，但 `CapBnd` 完整、`NoNewPrivs=0`，且用户属于 sudo/video 组并可免密 sudo。`/workspace` 中的产物保持主机用户所有权；标准 HOME 位于容器可写层，重建后重新创建，只有 `/workspace/.dev_bash_history` 持久化。

2. 将差异分成“通用创建风格”和“业务参数”。统一前者，只保留能够说明用途的后者，例如基础镜像、依赖、工程命名、GPU 选择及业务环境变量。
3. 不复制参考工程的 RKNN、YOLO、Ultralytics 等业务配置；也不要为了缓存便利全局覆盖 `HOME` 或 `HF_HOME`。缓存应由具体下载命令限定到输出目录，或使用框架自己的独立业务变量。
4. 明确评估 host namespace、privileged、设备/目录挂载、免密 sudo 和 sysctl 的影响。若新工程不需要这些能力，应形成单独的安全方案，而不是只删除其中一项后仍宣称与本基线等价。
5. 修改后依次验证 shell 语法、Compose 渲染、账户幂等性、实际容器 HostConfig、HOME/工具、依赖、GPU 和项目测试；最后同步 README、使用手册和更新日志。`start/restart` 会重建或进入容器，执行前先确认没有训练任务。
